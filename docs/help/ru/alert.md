# Конфигурация алертов: alert.json

## Простое объяснение (для новичков)

Этот файл — «настройки тревожной кнопки». Он говорит системе, при каких условиях отправлять уведомление, а при каких — молчать.

**Что внутри:**

- `hours` — за сколько часов смотреть данные (по умолчанию 24).
- `topic_gap_threshold` — при скольких упоминаниях темы считать её «значимой» (по умолчанию 20).
- `sync_threshold` — при скольких источниках одновременно считать событие «синхронным» (по умолчанию 5).
- `framing_threshold` — при какой разнице тональностей считать «поляризацией» (по умолчанию 0.7).

**Зачем это нужно:**

Если поставить слишком низкие пороги — система будет «спамить» алертами на каждую мелочь. Если слишком высокие — пропустит важное. Этот файл позволяет настроить баланс под конкретный поток данных.

**Как менять:**

Откройте файл в любом текстовом редакторе, измените числа, сохраните. Перезапуск не нужен — модуль `alert-dispatcher-api.mjs` перечитывает конфиг при каждом запуске.

## Научная база (для специалистов)

Конфигурационный файл задаёт параметры статистических детекторов, работающих на таблицах `information_gaps`, `topic_gaps`, `coordinated_actions`, `framing_gaps`.

**Поля конфигурации:**

- `hours` — размер временного окна (в часах). Определяет, за какой период анализируются данные. Малое окно (1–6 ч) — реакция на «горячие» события. Большое (48–168 ч) — фоновый анализ.
- `topic_gap_threshold` — порог «значимости» темы. Если тема упоминается реже этого порога — она считается «фоновой» и не поднимает алерт. Это защита от спама по редким темам.
- `sync_threshold` — минимальное число источников, публикующих событие одновременно, чтобы считать его «синхронным». Значение 5 отсекает случайные совпадения (3 источника могут совпасть случайно).
- `framing_threshold` — минимальная разница полярности (`|polarity_russian - polarity_western|`) для алерта «framing_gap». Значение 0.7 означает «сильная поляризация».

**Формально:** файл задаёт пороги для бинарных классификаторов, работающих на непрерывных метриках. Каждый порог — это компромисс между полнотой (recall) и точностью (precision).

---

## Как работает (пошагово)

1. `alert-dispatcher-api.mjs` при запуске читает `config/alert.json`.
2. Для каждого триггера (`silence_gap`, `topic_gap`, `coordinated_event`, `framing_gap`, `feed_failure`) проверяет соответствующее условие с порогом из конфига.
3. Если условие выполнено — создаётся объект алерта.
4. Алерт сохраняется в таблицу `alerts` (если настроено) или отправляется в Telegram/webhook.
5. При следующем запуске конфиг перечитывается — изменения применяются без перезапуска сервера.

## Пример использования

**Стандартный конфиг (для потока 300–500 статей в сутки):**

```json
{
  "hours": 24,
  "topic_gap_threshold": 20,
  "sync_threshold": 5,
  "framing_threshold": 0.7
}

Чувствительный конфиг (для малого потока или раннего предупреждения):
json

{
  "hours": 12,
  "topic_gap_threshold": 10,
  "sync_threshold": 3,
  "framing_threshold": 0.5
}

Консервативный конфиг (для большого потока, защита от спама):
json

{
  "hours": 48,
  "topic_gap_threshold": 40,
  "sync_threshold": 8,
  "framing_threshold": 0.85
}

Практические рекомендации

    hours: 24 — оптимально для суточного цикла новостей. Меньше — растёт шум, больше — теряется реактивность.

    topic_gap_threshold: 20 — при 300–500 статьях в сутки. Для потока 100 статей — снижайте до 10.

    sync_threshold: 5 — 3 источника могут совпасть случайно (погода, курсы валют). 5 — уже устойчивый сигнал.

    framing_threshold: 0.7 — сильная поляризация. При 0.5 — «умеренная», при 0.85 — «экстремальная».

    Не ставьте sync_threshold: 2 — пара источников почти всегда совпадает. Это не сигнал.

    Держите конфиг под версионным контролем — изменение порогов меняет результаты. Фиксируйте версию в отчётах.

    Калибруйте на исторических данных — прогоните систему с разными порогами на данных за прошлый месяц и сравните: где алерты были полезны, а где — шум.
