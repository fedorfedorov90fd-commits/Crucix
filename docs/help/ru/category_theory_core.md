# Теория категорий: category_theory_core.py

## Простое объяснение (для новичков)

Этот файл — «универсальный конструктор» системы. Он описывает архитектуру Crucix не как набор папок с кодом, а как математическую структуру, где всё соединяется через стандартные «переходники».

**Что он делает:**

Представьте, что у вас есть конструктор Лего. Есть кирпичики разных форм (данные), и есть пазы (функции преобразования). Если кирпичик подходит к пазу — он защёлкивается. Неважно, какого он цвета и откуда взят.

В Crucix:
- **Объекты** — это типы данных: сырой RSS, нормализованный JSON, запись в БД, вектор эмбеддинга.
- **Морфизмы** — это функции преобразования: `normalize_rss`, `save_news`, `encode_embedding`.
- **Композиция** — это когда две функции соединяются в цепочку: `save_news ∘ normalize_rss` = «из RSS сразу в БД».

**Зачем это нужно:**

В обычной программе замена одного компонента (например, RSS-ридера на другой) ломает всё, что с ним связано. В категориальном подходе — нет. Если новый ридер даёт на выходе тот же тип данных (JSON), вся остальная цепочка работает без изменений.

**Аналогия:**

Это как переходники для розеток. Розетка в стене — одна. Вилки у приборов — разные. Переходник позволяет подключить любой прибор к любой розетке. Морфизм — это такой переходник.

## Научная база (для специалистов)

Теория категорий — раздел абстрактной алгебры, изучающий объекты через их связи (морфизмы), а не через внутреннее устройство. Ключевые понятия:

- **Объекты** — типы данных: `RawRSS`, `JsonNews`, `DbRecord`, `Embedding`.
- **Морфизмы** — функции преобразования: `normalize_rss: RawRSS → JsonNews`.
- **Композиция** `g ∘ f` — если есть `f: A → B` и `g: B → C`, то их композиция даёт `g ∘ f: A → C`.
- **Законы категории:** ассоциативность (`h ∘ (g ∘ f) = (h ∘ g) ∘ f`) и существование единичного морфизма (`id: A → A`).

**Реализация на Python:**

- Используются типовые переменные (`TypeVar`) для декларации совместимости типов на входе и выходе.
- Библиотека `arrow` (функциональный стиль) позволяет строить композиции-«трубопроводы», которые невозможно собрать некорректно.
- Чистые функции без побочных эффектов делают систему полностью тестируемой.

**Почему это важно для архитектуры:**

- **Слабая связанность (loose coupling):** замена одного морфизма не затрагивает остальные, если сохраняется тип.
- **Тестируемость:** каждый морфизм проверяется отдельно, а конвейер — как композиция.
- **Расширяемость:** при добавлении нового источника достаточно реализовать один морфизм, не трогая остальную архитектуру.
- **Воспроизводимость:** чистые функции всегда возвращают одно и то же для одного входа — результаты воспроизводимы.

## Как работает (пошагово)

1. Объявляются типовые переменные `T`, `U`, `V` — правила совместимости данных.
2. Определяются морфизмы: например, `normalize_rss: RawRSS → JsonNews`, `save_news: JsonNews → DbRecord`.
3. Функция `compose(f, g)` строит композицию: `save_news ∘ normalize_rss` — защищённый канал «RSS → БД».
4. Замена `normalize_rss` на другой морфизм того же типа не затрагивает `save_news`.
5. Чистые функции (без побочных эффектов) обеспечивают воспроизводимость и лёгкое тестирование.
6. Оркестратор собирает конвейер из композиций морфизмов.

**Пример композиции:**

```python
# Морфизмы
def normalize_rss(raw: RawRSS) -> JsonNews: ...
def save_news(json: JsonNews) -> DbRecord: ...
def encode_embedding(db: DbRecord) -> Embedding: ...

# Композиция: RSS → JSON → БД → Embedding
pipeline = compose(encode_embedding, compose(save_news, normalize_rss))

# Применение
result = pipeline(raw_rss)  # Embedding

Пример использования
python

from services.category_theory_core import compose, normalize_rss, save_news

# Сборка конвейера: RSS → БД
pipeline = compose(save_news, normalize_rss)

# Применение к сырым данным
raw_rss = fetch_feed("https://example.com/feed.xml")
db_record = pipeline(raw_rss)

Что происходит:

    normalize_rss(raw_rss) превращает сырой RSS в нормализованный JSON.

    save_news(json) сохраняет JSON в БД и возвращает запись.

    Обе функции чистые: не зависят от глобального состояния, не имеют побочных эффектов (кроме save_news, который пишет в БД — но это вынесено в отдельный морфизм).

Практические рекомендации

    Держите морфизмы чистыми. Побочные эффекты (запись в БД, сеть) выносите в отдельные функции-адаптеры. Это упрощает тестирование и отладку.

    Типовые аннотации — не формальность. Они ловят несовместимости на этапе разработки, а не в проде. Если функция ожидает JsonNews, а получает RawRSS — ошибка будет видна сразу.

    При добавлении нового источника достаточно реализовать один морфизм. Не трогайте остальную архитектуру.

    Композиция упрощает тестирование: каждый морфизм проверяется отдельно, а конвейер — как композиция. Если тест на морфизм проходит — композиция работает.

    Документируйте типы морфизмов — это и есть «контракт» между компонентами системы. Без контракта композиция ломается.

    Не злоупотребляйте теорией категорий. Это инструмент для архитектуры, а не для каждой функции. Применяйте там, где есть цепочки преобразований (RSS → JSON → БД → Embedding), а не к одиночным операциям.

    Композиция не заменяет оркестратор. Оркестратор решает, когда запускать конвейер. Композиция решает, как соединить шаги.
