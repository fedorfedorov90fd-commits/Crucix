# Конфигурация сравнения нарративов: contrast.json

## Простое объяснение (для новичков)

Этот файл — «настройки» для модуля, который сравнивает, как разные группы источников описывают одно и то же событие. Он говорит системе: «Сравнивай нарративы за последние 24 часа, и считай тему значимой, если у неё есть хотя бы одно событие с каждой стороны».

**Что внутри:**

```json
{
  "hours": 24,
  "min_events_per_topic": 1
}

    hours — за сколько часов смотреть данные (по умолчанию 24).

    min_events_per_topic — сколько событий должно быть у каждой группы, чтобы тема попала в сравнение (по умолчанию 1).

Зачем это нужно:

Сравнивать нарративы можно только там, где есть что сравнивать. Если о теме пишет только одна сторона — это не «сравнение», это «молчание» (другой детектор). Модуль contrast работает только с теми темами, где обе стороны что-то сказали.

Аналогия:

Представьте, что вы сравниваете два блюда. Если одно блюдо есть, а другого нет — вы не можете сказать, какое вкуснее. Вы можете только сказать: «второго блюда нет». Сравнение начинается только тогда, когда есть оба блюда. min_events_per_topic: 1 — это минимальное условие: хотя бы по одному событию с каждой стороны.
Научная база (для специалистов)

Конфигурационный файл задаёт параметры детектора поляризации нарративов, реализованного в scripts/analyzers/contrast-engine.mjs (слитом в narrative-splitter-api.mjs).

Поля конфигурации:

    hours — размер временного окна (в часах). Определяет, за какой период анализируются события. Малое окно (6–12 ч) — реакция на «горячие» события. Большое (48–72 ч) — фоновый анализ.

    min_events_per_topic — минимальное число событий у каждой группы (russian и western), чтобы тема попала в сравнение. Защита от сравнения «пустоты с пустотой».

Формально:

Для каждой темы t вычисляются:

    russian_events(t) — число событий темы t у группы russian.

    western_events(t) — число событий темы t у группы western.

Тема попадает в сравнение, если:

    russian_events(t) ≥ min_events_per_topic И

    western_events(t) ≥ min_events_per_topic.

Для таких тем вычисляется:

    polarity_russian — средняя тональность заголовков у russian.

    polarity_western — средняя тональность заголовков у western.

    polarity_delta = |polarity_russian - polarity_western| — разница.

    latency_hours — медиана разницы first_published между группами.

Классификация:

    framing_gap — polarity_delta > 0.3 (разная тональность).

    reaction_gap — |latency_hours| > 6 (одна сторона опаздывает).

    both — и то, и другое.

    severity: high — если polarity_delta > 0.5 или |latency_hours| > 12.

Почему min_events_per_topic: 1:

На текущих данных (300–500 статей в сутки, 2 западных фида из 7) многие темы имеют western_events = 0. Если поставить порог 2 или 3 — большинство тем выпадет из сравнения. Порог 1 — компромисс: сравниваем там, где есть хоть что-то с каждой стороны.

Ограничения:

    polarity на словаре (~200 слов) — грубо. Контекст «санкции против врага» = позитив, но словарь ставит негатив.

    reaction_gap требует событий, которые есть и у russian, и у western. На текущих данных таких мало.

    ML-подход (эмбеддинги) даст больше, но требует nlp_semantic_core.py.

Как работает (пошагово)

    contrast-engine.mjs при запуске читает config/contrast.json.

    Загружает события за hours часов.

    Для каждой темы считает russian_events и western_events.

    Если оба ≥ min_events_per_topic — тема попадает в сравнение.

    Для каждой такой темы вычисляет polarity_russian, polarity_western, polarity_delta, latency_hours.

    Классифицирует: framing_gap, reaction_gap, both, none.

    Сохраняет в таблицу framing_gaps.

Что происходит при изменении порога:

    Уменьшение min_events_per_topic до 1 → больше тем в сравнении.

    Увеличение до 3 → меньше тем, но сравнение надёжнее (статистически).

    Уменьшение hours до 6 → реакция на «горячие» события.

    Увеличение hours до 72 → фоновый анализ, меньше шума.

Пример использования

Стандартный конфиг (для потока 300–500 статей в сутки):
json

{
  "hours": 24,
  "min_events_per_topic": 1
}

Чувствительный конфиг (для малого потока или раннего предупреждения):
json

{
  "hours": 12,
  "min_events_per_topic": 1
}

Консервативный конфиг (для большого потока, статистическая надёжность):
json

{
  "hours": 48,
  "min_events_per_topic": 3
}

Применение:
bash

# Изменить конфиг
nano config/contrast.json

# Пересобрать framing_gaps
psql -d crucix -c "DELETE FROM framing_gaps;"
node scripts/analyzers/contrast-engine.mjs

Практические рекомендации

    hours: 24 — оптимально для суточного цикла новостей. Меньше — растёт шум, больше — теряется реактивность.

    min_events_per_topic: 1 — на текущих данных (мало западных фидов). При расширении до 43+ фидов можно поднять до 2–3.

    Не ставьте min_events_per_topic: 0 — это бессмысленно: сравнение пустоты с пустотой.

    Не ставьте hours > 72 — события за неделю слишком разнородны, сравнение теряет смысл.

    Калибруйте на исторических данных — прогоните систему с разными порогами на данных за прошлый месяц и сравните: где сравнение было полезным, а где — шум.

    polarity на словаре — грубо. Если нужна точность — используйте nlp_semantic_core.py (эмбеддинги).

    framing_gaps сохраняются в БД — можно отслеживать динамику: как менялась поляризация по теме во времени.

    DELETE FROM framing_gaps перед пересборкой — метрика пересчитываемая, накопление даёт дубликаты.

    Держите конфиг под версионным контролем — изменение порогов меняет результаты. Фиксируйте версию в отчётах.
