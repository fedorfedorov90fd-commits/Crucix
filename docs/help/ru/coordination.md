# Конфигурация координации источников: coordination.json

## Простое объяснение (для новичков)

Этот файл — «настройки» для модуля, который ищет источники, публикующие новости **синхронно**. Он говорит системе: «Считай событие синхронным, если его опубликовали минимум 3 источника в пределах 6 часов, и пару источников — устойчивой, если они совпали минимум 3 раза».

**Что внутри:**

```json
{
  "hours": 24,
  "min_sources": 3,
  "max_spread_minutes": 360,
  "min_co_occurrences": 3
}

    hours — за сколько часов смотреть данные (по умолчанию 24).

    min_sources — сколько источников должно опубликовать событие одновременно, чтобы считать его «синхронным» (по умолчанию 3).

    max_spread_minutes — максимальный разброс времени между публикациями (по умолчанию 360 минут = 6 часов).

    min_co_occurrences — сколько раз пара источников должна встретиться, чтобы считаться «устойчивой» (по умолчанию 3).

Зачем это нужно:

Если два источника всегда публикуют вместе — это может быть нормальная синдикация (РИА и ТАСС перепечатывают друг друга). А может быть — скоординированная кампания. Этот файл позволяет настроить чувствительность: как часто должна встречаться пара, чтобы попасть в отчёт.

Аналогия:

Представьте, что вы наблюдаете за двумя людьми в кафе. Если они случайно оказались за одним столиком один раз — это совпадение. Если они сидят вместе каждый день в одно и то же время — это уже паттерн. min_co_occurrences: 3 — это порог: «минимум 3 раза вместе, чтобы считать это паттерном».
Научная база (для специалистов)

Конфигурационный файл задаёт параметры детектора координации источников, реализованного в scripts/analyzers/source-coordination.mjs (слитом в apis/sources/source-coordination-api.mjs).

Поля конфигурации:

    hours — размер временного окна (в часах). Определяет, за какой период анализируются события.

    min_sources — минимальное число источников, публикующих событие одновременно, чтобы считать его «синхронным». Значение 3 отсекает случайные совпадения (пара источников может совпасть случайно).

    max_spread_minutes — максимальный временной разброс между первой и последней публикацией события. Значение 360 минут (6 часов) — реалистично для RSS, где публикации приходят с задержкой в часы, а не минуты.

    min_co_occurrences — минимальное число совместных публикаций пары источников, чтобы считать пару «устойчивой». Значение 3 — компромисс между чувствительностью и защитой от случайных совпадений.

Формально:

Для каждой пары источников (A, B) вычисляется co_occurrences(A, B) — число событий, где оба источника опубликовали материал в пределах max_spread_minutes.

Пара считается «устойчивой», если co_occurrences(A, B) ≥ min_co_occurrences.

Событие считается «синхронным», если:

    sources_count ≥ min_sources И

    spread_minutes ≤ max_spread_minutes.

Почему max_spread_minutes: 360, а не 60:

RSS-фиды публикуют с задержкой. Например, РИА публикует в 07:37, ТАСС — в 12:12. Разница — 4.5 часа. Если поставить порог 60 минут, такие события не попадут в «синхронные». Порог 360 минут (6 часов) — реалистичен для RSS. Для Telegram-каналов порог был бы 5–10 минут.

Почему min_sources: 3:

Два источника могут совпасть случайно (погода, курсы валют). Три источника — уже устойчивый сигнал. Если поставить min_sources: 2, система будет находить «синхронность» там, где её нет.

Почему min_co_occurrences: 3:

Одна совместная публикация — случайность. Две — совпадение. Три — паттерн. Это эмпирическое значение, полученное на корпусе из ~300 событий.

# Конфигурация координации источников: coordination.json

## Простое объяснение (для новичков)

Этот файл — «настройки» для модуля, который ищет источники, публикующие новости синхронно. Он говорит системе: «Считай источники скоординированными, если они пишут об одном событии в пределах стольких-то минут, и таких совпадений было столько-то раз».

**Что внутри:**

```json
{
  "hours": 24,
  "min_sources": 3,
  "max_spread_minutes": 360,
  "min_co_occurrences": 3
}

    hours — за сколько часов смотреть данные (по умолчанию 24).

    min_sources — сколько источников должно участвовать в событии, чтобы считать его «синхронным» (по умолчанию 3).

    max_spread_minutes — максимальный разброс времени между первой и последней публикацией (по умолчанию 360 минут = 6 часов).

    min_co_occurrences — сколько раз пара источников должна встретиться, чтобы считаться «устойчивой» (по умолчанию 3).

Зачем это нужно:

Если два источника один раз случайно опубликовали новость одновременно — это не координация. Если они делают это 17 раз за сутки — это уже паттерн. Файл задаёт пороги, которые отделяют случайность от паттерна.

Аналогия:

Представьте, что вы наблюдаете за двумя людьми в кафе. Один раз они пришли одновременно — совпадение. Пять раз за неделю — уже привычка. Десять раз — возможно, они коллеги. Пороги в этом файле — это способ отличить «случайно» от «систематически».
Научная база (для специалистов)

Конфигурационный файл задаёт параметры детектора координации источников, реализованного в apis/sources/source-coordination-api.mjs.

Поля конфигурации:

    hours — размер временного окна (в часах). Определяет, за какой период анализируются события. Малое окно (6–12 ч) — реакция на «горячие» события. Большое (48–72 ч) — фоновый анализ.

    min_sources — минимальное число источников, публикующих событие одновременно, чтобы считать его «синхронным». Значение 3 отсекает случайные пары (два источника могут совпасть случайно).

    max_spread_minutes — максимальный временной разброс между первой и последней публикацией события. Значение 360 (6 часов) — реалистично для RSS. 60 минут — порог для Telegram, а не для RSS.

    min_co_occurrences — минимальное число совместных публикаций пары источников, чтобы считать пару «устойчивой». Значение 3 отсекает случайные совпадения.

Формально:

Для каждого события e вычисляется:

    sources_count(e) — число уникальных источников, опубликовавших событие.

    spread(e) = max(published_at) - min(published_at) — временной разброс.

Событие считается «синхронным», если:

    sources_count(e) ≥ min_sources И

    spread(e) ≤ max_spread_minutes.

Для каждой пары источников (A, B) считается co_occurrences(A, B) — сколько раз они публиковали одно событие синхронно. Пара считается «устойчивой», если co_occurrences(A, B) ≥ min_co_occurrences.

Почему max_spread_minutes: 360, а не 60:

RSS-фиды публикуют с задержкой. Пример: РИА публикует в 07:37, ТАСС — в 12:12. Разница — 4.5 часа. Если поставить порог 60 минут — это событие не попадёт в «синхронные», хотя оба источника написали об одном и том же. Порог 360 минут (6 часов) — реалистичен для RSS.

Для Telegram-каналов порог 60 минут был бы правильным: там публикации идут в реальном времени. Но для RSS — 360.

Ограничения:

    max_spread_minutes зависит от типа источника. Для RSS — 360, для Telegram — 60, для Twitter — 30.

    min_co_occurrences: 3 — на текущих данных (300–500 статей в сутки) пара ria-world ↔ tass-world даёт 17 co-occurrences. Это нормальная синдикация. Появление новой пары (ТАСС + неизвестный фид с 5+) — сигнал.

    sync events на текущих данных — 2 (Росстат, БПЛА). Мало, потому что западных фидов мало (2 из 7).

Как работает (пошагово)

    source-coordination-api.mjs при запуске читает config/coordination.json.

    Загружает события за hours часов с sources_count ≥ 2.

    Для каждого события считает sources_count и spread.

    Если sources_count ≥ min_sources и spread ≤ max_spread_minutes — событие «синхронное».

    Строит матрицу пар: (feed_A, feed_B) → co_occurrences.

    Пары с co_occurrences ≥ min_co_occurrences — «устойчивые».

    Сохраняет в таблицу coordinated_actions:

        source_pair — для устойчивых пар.

        synchronous_event — для синхронных событий.

Что происходит при изменении порога:

    Уменьшение min_sources до 2 → больше «синхронных» событий, но больше шума.

    Увеличение max_spread_minutes до 720 → больше событий, но менее строгая синхронность.

    Уменьшение min_co_occurrences до 2 → больше пар, но менее устойчивых.

Пример использования

Стандартный конфиг (для RSS-потока):
json

{
  "hours": 24,
  "min_sources": 3,
  "max_spread_minutes": 360,
  "min_co_occurrences": 3
}

Для Telegram-потока (более строгий):
json

{
  "hours": 24,
  "min_sources": 3,
  "max_spread_minutes": 60,
  "min_co_occurrences": 3
}

Для фонового анализа (менее строгий):
json

{
  "hours": 72,
  "min_sources": 2,
  "max_spread_minutes": 720,
  "min_co_occurrences": 2
}

Применение:

# Изменить конфиг

Практические рекомендации

    max_spread_minutes: 360 — реалистично для RSS. 60 минут — порог для Telegram, а не для RSS.

    min_sources: 3 — 3 источника — это уже не случайность. 2 источника могут совпасть случайно (погода, курсы валют).

    min_co_occurrences: 3 — пара должна встретиться минимум 3 раза, чтобы считаться устойчивой.

    ria-world ↔ tass-world: 17 — нормальная синдикация двух главных лент. Появление новой пары (ТАСС + неизвестный фид с 5+) — сигнал.

    sync events: 2 — Росстат (3src/82min), Нижегородская БПЛА (3src/205min). Мало, потому что западных фидов мало (2 из 7).

    DELETE FROM coordinated_actions перед пересборкой — метрика пересчитываемая, накопление даёт дубликаты.

    max_spread_minutes зависит от типа источника. Для RSS — 360, для Telegram — 60, для Twitter — 30. Не переносите пороги между типами источников.

    min_co_occurrences: 2 — для малого потока (100 статей в сутки). Для большого (1000+) — 5.

    Держите конфиг под версионным контролем — изменение порогов меняет результаты. Фиксируйте версию в отчётах.
