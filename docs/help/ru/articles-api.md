# API статей: articles-api.mjs

## Простое объяснение (для новичков)

Этот файл — «раздача» новостей для всех, кто их запрашивает. Виджет на дашборде, мобильное приложение, скрипт аналитика — все они приходят сюда и говорят: «Дай мне 20 последних статей». Этот модуль идёт в хранилище, берёт данные и возвращает в понятном виде.

**Что он делает:**

1. **Читает данные** из «корзины» — файлов `rsshub.json`, `rss-latest.json`, `rss-universal.json`, `rss.json`. Если первый пуст — берёт второй, и так далее.
2. **Фильтрует** по параметрам запроса: сколько статей (`limit`), за какой период, от какого источника.
3. **Сортирует** по времени публикации (свежие — первыми).
4. **Отдаёт** в формате JSON: массив статей с полями `title`, `link`, `source`, `published_at`, `group`, `content`.

**Зачем это нужно:**

В системе 226+ сборщиков и 59+ анализаторов. Если каждый из них будет напрямую читать файлы, получится хаос. API-модуль — это «единая точка входа»: все запрашивают данные одинаково, получают одинаковый формат.

**Аналогия:**

Это как библиотекарь. Вы говорите: «Мне нужны 20 последних книг по истории». Библиотекарь идёт в хранилище, находит, сортирует по дате, приносит. Вы не знаете, где именно лежала каждая книга — вы просто получаете результат.

## Научная база (для специалистов)

Модуль реализует паттерн **Repository / Gateway**: единая точка доступа к данным с абстракцией над источником. Это стандартный подход в архитектурах, где данные могут приходить из разных мест (файлы, БД, внешние API) — клиент не знает, откуда именно пришли данные.

**Архитектура:**

- **Fallback-цепочка:** `rsshub.json → rss-latest.json → rss-universal.json → rss.json`. Это защита от ситуации, когда один файл пуст (например, `collect-rsshub.mjs` ещё не отработал), а данные нужны сейчас.
- **Кеширование:** результат кешируется на 2 минуты (`CACHE_TTL_MS`). Повторные запросы в течение этого окна не читают файлы заново — это важно для дашбордов, которые обновляются каждые 5 минут.
- **Нормализация:** каждый item приводится к единому формату: `title`, `link`, `source`, `published_at`, `group`, `content`, `id`. Даже если в исходном файле поля называются по-разному, API отдаёт одинаковый формат.
- **Фильтрация и сортировка:** на уровне API, а не на клиенте. Это снижает нагрузку на клиентов и делает поведение предсказуемым.

**Контракт v2:**

Модуль соответствует контракту Crucix v2: экспортирует `route`, `method`, `meta`, `handler`. Это позволяет роутеру автоматически подхватить модуль при пересборке реестра.

## Как работает (пошагово)

1. `handler(req, res)` принимает HTTP-запрос.
2. Парсит `query` (параметры запроса): `limit`, `source`, `hours`, `q`.
3. Проверяет кеш: если данные есть и не устарели (2 минуты) — возвращает их сразу.
4. Если кеша нет — перебирает fallback-цепочку файлов, пока не найдёт непустой.
5. Если ни один файл не найден — возвращает пустой массив с `error: 'not_found'`.
6. Нормализует каждый item: приводит поля к единому формату.
7. Применяет фильтры: по источнику, по времени, по поисковому запросу.
8. Сортирует по `published_at` (свежие — первыми).
9. Ограничивает `limit` (по умолчанию 100).
10. Возвращает JSON: `{ count, total, items, _meta }`.

**Подпути:**

- `GET /api/layers/articles` — корень (список статей).
- `GET /api/layers/articles/stats` — агрегаты (сколько статей, сколько источников, сколько групп).
- `GET /api/layers/articles/status` — health-check (доступен ли API).
- `GET /api/layers/articles/groups` — группировка по `russian / western / neutral`.
- `GET /api/layers/articles/sources` — список источников с количеством.
- `GET /api/layers/articles/raw` — сырые items (первые 50) для отладки.

## Пример использования

**Базовый запрос:**

```bash
curl "http://127.0.0.1:3117/api/layers/articles?limit=20"

С фильтром по источнику:
bash

curl "http://127.0.0.1:3117/api/layers/articles?source=ТАСС&limit=10"

С фильтром по времени:
bash

curl "http://127.0.0.1:3117/api/layers/articles?hours=6&limit=50"

Пример ответа:

Практические рекомендации

    Fallback-цепочка — не удаляйте старые файлы (rss.json, rss-universal.json). Они нужны, если новые (rsshub.json) пусты.

    Кеш 2 минуты — не увеличивайте без необходимости. Дашборд обновляется каждые 5 минут, кеш в 2 минуты даёт «свежесть» без лишних чтений.

    limit по умолчанию 100 — защита от «дай всё сразу». Если нужно больше — указывайте явно (?limit=500).

    Сортировка по published_at — если published_at отсутствует (битая дата), статья уходит в конец. Это не баг — это норма: лучше показать её последней, чем первой.

    group — russian, western, neutral. Используется для цветовой кодировки в виджетах.

    /raw — для отладки. Не используйте в продакшене: он отдаёт первые 50 items без фильтров и сортировки.

    /status — health-check. Если API недоступен, виджеты показывают «нет данных», а не падают.

    Нормализация полей — если источник присылает pubDate вместо published_at, API приводит к единому виду. Клиенты не должны об этом думать.

    Контракт v2 — при добавлении новых полей не ломайте существующие. Клиенты полагаются на текущий формат.
