# 002. Стратегия миграции существующих справок

Дата: 2026-09-26
Статус: accepted
Уровень уверенности: высокий

Контекст

В docs/help/ru/ находится 690 файлов справок, в docs/help/en/ — 697. Структура накопительная: файлы с суффиксами _0, _1, _2, знаками равно в именах, дубли имён. Каталог reference/collectors/ содержит 1 файл вместо 118 (по числу сборщиков). Каталог reference/apis/ пустой. Каталог reference/analyzers/ пустой.

Одновременно создан новый фундамент справок по стандарту Diataxis: docs/help/README.md, INDEX.md, CONTRIBUTING.md, _templates/, reference/{collectors,apis,analyzers,contract}/, how-to/, explanation/decisions/, tutorials/.

Требуется стратегия переноса 690+697 файлов из старой структуры в новую без потери данных и без разрушения работающей системы.

Рассмотренные варианты

Вариант A. Полный единовременный аудит и миграция. Плюсы: единая структура сразу. Минусы: огромный объём работы, высокий риск ошибок, простой в работе со справками на дни/недели.

Вариант B. Оставить старую структуру, новые справки только в новой. Плюсы: нет риска. Минусы: две параллельные структуры навсегда, путаница где искать.

Вариант C. Паттерн Strangler Fig. Плюсы: старая структура работает, новая растёт параллельно, миграция по мере касания файлов, отсутствие простоя, контролируемый прогресс. Минусы: временное сосуществование двух структур.

Решение

Выбран вариант C — паттерн Strangler Fig (Мартин Фаулер, martinfowler.com/bliki/StranglerFigApplication.html).

Принцип: старая система продолжает работать, новая растёт вокруг неё. Постепенно новая структура охватывает всё большую часть, старая сокращается. Когда миграция завершена — старая архивируется (не удаляется, правило 1070).

Применение в Crucix:

1. Старая структура docs/help/ru/ и docs/help/en/ работает как есть. Ничего не удаляется, не перемещается массово.

2. Новая структура docs/help/reference/, how-to/, explanation/, tutorials/ развивается при создании каждой новой справки или при касании существующей.

3. Правило касания: если файл старой структуры требует изменений — он переписывается в новой структуре по стандарту Diataxis. Старый файл остаётся до явного решения об архивации.

4. INDEX.md новой структуры пополняется ссылками по мере миграции.

5. Когда файлов старой структуры станет мало — они переносятся в archive-docs/ (единый архив, не удаляются).

Правила именования при миграции:

- Суффиксы _0, _1, _2, знак равно — устраняются. Файл приводится к чистому имени.
- Дубли имён — синтез в один файл (правило 1070). Не выбор, не архив, только синтез.
- Каждый файл получает тип по Diataxis (Reference, How-to, Explanation, Tutorial) и место в соответствующем каталоге.

Последствия

Что это даёт:

- Работающая старая структура не ломается.
- Новая структура растёт параллельно, без простоя.
- Прогресс контролируемый: миграция идёт по мере касания файлов.
- Правило 1070 соблюдено: старые файлы не удаляются, дубли синтезируются.

Что это ограничивает:

- Временно две структуры сосуществуют.
- Требуется дисциплина: при касании любого файла — миграция в новую структуру.

Компромиссы:

Осознанно принимаем временное сосуществование двух структур ради отсутствия риска и простоя.
