как было бы лучше всего если бы было сделано максимально профессионально?
Отвечу не «как обычно делают костыли», а как делают большие команды в зрелых OSINT-платформах. Это будет длинный, но конкретный архитектурный ответ.

Что сломано сейчас — одним предложением
В проекте три слоя (роутер, реестр, фронтенд) говорят на трёх разных языках, и между ними нет контракта. Любая новая фича будет ломаться так же, как dxy.

Как было бы сделано максимально профессионально
Принцип 1. Единый контракт между модулем и роутером
В зрелой архитектуре не бывает 5 форм экспорта. Есть один канон, задокументированный в docs/API_CONTRACT.md:

js
 Run JS
// apis/sources/example-api.mjs
export const route  = '/api/layers/example';      // обязательное поле
export const method = 'GET';                       // опционально, по умолчанию GET
export const meta   = { cache: 60, schema: 'FeatureCollection' };
export async function handler(req, res) { ... }   // обязательное поле
Только handler — каноничное имя. Всё остальное — deprecated.

Плюс инструмент проверки tools/lint-api-modules.mjs, который при npm run lint:api проходит по всем *-api.mjs и выдаёт список нарушителей. CI (или pre-commit hook) не пускает коммит, если модуль нарушает контракт.

Что это даёт: невозможно добавить модуль, который роутер не поймёт. Ошибка обнаруживается на этапе написания, а не на этапе «пользователь открыл карту и увидел 500».

Принцип 2. Реестр — не ручной JSON, а генерируемый артефакт
Сейчас routes-api.json — это 329 записей, которые кто-то руками поддерживает. И они не совпадают с реальностью (180 из 238 id слоёв отсутствуют).

Профессионально:

Единственный источник истины — сам файл модуля (export const route).

server/routes-api.json — генерируемый файл. Его создаёт scripts/build-registry.mjs, который сканирует apis/sources/*-api.mjs, читает route, method, meta и собирает реестр.

В package.json добавлен скрипт npm run build:registry.

Файл помечен в .gitignore как артефакт (или, если нужен в репозитории, то автоматически регенерируется в pre-commit hook и коммитится).

Проверка: npm run build:registry -- --check — если реестр разошёлся с источниками, exit code 1.

Что это даёт: рассинхрон реестра и модулей физически невозможен. Если добавил модуль — реестр сам знает о нём.

Принцип 3. Frontend-слои — декларативно, а не руками
Сейчас layers.js — это массив из 238 объектов, вручную поддерживаемый. Из них 180 ссылаются на несуществующие URL.

Профессионально:

Файл dashboard/public/geo-map/js/layers.js не содержит списка слоёв. Он содержит функцию загрузки и логику отображения.

Список слоёв приходит с сервера: GET /api/registry/layers — тот самый реестр, который сгенерирован из модулей.

Клиент при загрузке страницы дёргает /api/registry/layers и строит панель. Категории, иконки, цвета — из meta в модуле.

Если нужно скрыть слой — в meta ставится hidden: true. Если нужно показать только часть — category: 'finance' фильтруется на клиенте.

Что это даёт: нельзя завести слой, которого нет. Нельзя завести модуль, который не отображается. Панель слоёв = отражение реальности.

Принцип 4. Единый ответ API
Сейчас ответы разные:

{ success: true, data: [...] } (dxy, firms)

{ type: 'FeatureCollection', features: [...] } (вероятно, часть слоёв)

Возможно, где-то чистый массив или чистый объект.

Профессионально:

Один формат для слоёв: GeoJSON FeatureCollection — потому что карта (Leaflet) работает с ним напрямую.

Единая обёртка для метаданных: { type: 'FeatureCollection', meta: { source, updated_at, count, imputed_fields }, features: [...] }.

Все адаптеры (не-GeoJSON источники) приводятся к FeatureCollection в слое данных — в basket-adapter.mjs, а не на клиенте.

Роутер проверяет Content-Type и не отдаёт «сырой» массив как слой.

Что это даёт: клиент всегда знает форму ответа. markers.js не спотыкается на conflicts.slice is not a function.

Принцип 5. Контракт на ошибки
Сейчас 500 = «что-то упало», 404 = «модуль не найден или путь не совпал». Не различить «нет данных» от «нет модуля».

Профессионально — три разных ответа:

404 Not Found — модуля нет в реестре. Форма: { error: 'module_not_found', moduleId }.

503 Service Unavailable — модуль есть, но данных в корзине нет (сборщик ещё не отработал). Форма: { error: 'no_data', moduleId, hint: 'run scripts/collectors/collect-xxx.mjs' }.

500 Internal Error — модуль упал при выполнении. Форма: { error: 'handler_threw', moduleId, message, stack: '...' } — стек только в development.

Клиент различает эти состояния и, например, не пишет «модуль сломан», когда его просто ещё не запускали.

Что это даёт: диагностика становится однозначной. Логи и мониторинг могут считать «сколько модулей без данных» и «сколько модулей падает» — это разные метрики.

Принцип 6. Центральный логгер + телеметрия вызовов
Каждый вызов через роутер пишет структурированную строку:

json
{"ts":"2026-09-13T09:14:22Z","layer":"dxy","moduleId":"dxy-api","status":500,"duration_ms":12,"err":"entry.handler is not a function","form":"default_object"}
Где form — какая форма экспорта сработала (для аудита контракта). Эти логи идут в logs/api-requests.log и в Центр мониторинга (/monitor), где есть вкладка «API Health» со списком: какой слой сколько раз упал, за какое время, с какой ошибкой.

Что это даёт: проблемы видны сразу, не после «пользователь заметил».

Принцип 7. Тесты контракта
tests/api-contract.test.mjs:

Для каждого модуля в реестре — есть export function handler.

Для каждого модуля — route начинается с /api/.

Для каждого модуля — handler вызывается без ошибок на фиктивных req/res.

Для каждого слоя в UI-конфиге — URL существует в реестре.

Запуск: npm test — 30 секунд. Ловит все проблемы, которые мы ловили 2 дня через консоль браузера.

Что это даёт: регрессия невозможна. Меняешь 1 модуль — тест говорит, что поломалось и где.

Принцип 8. Соглашение об именах
Сейчас есть dxy-api.mjs, crucix-movements.mjs, map-layer-cyber.mjs, military-spending-api.mjs — всё вперемешку.

Профессионально — единый паттерн:

Класс-вычислитель: {name}.mjs (без -api).

HTTP-обёртка: {name}-api.mjs.

Collector: collect-{name}.mjs.

Analyzer: {name}.mjs в scripts/analyzers/.

Layer id (URL): {name} — без суффикса -api.

Регистрация в реестре: автоматически из {name}-api.mjs.

Тогда dxy-api.mjs → /api/layers/dxy — не нужно никаких хардкодов.

Принцип 9. Каждый слой знает, откуда данные
В meta модуля:

js
 Run JS
export const meta = {
  source: 'basket/dxy.json',
  collector: 'collect-dxy.mjs',
  updated_at: '...',   // динамически
  vizType: 'marker' | 'choropleth' | 'heatmap' | 'layer',
  category: 'finance',
  icon: '💵',
  color: '#0cf'
};
Это всё попадает в /api/registry/layers. Клиент строит панель сама. Слой знает сам о себе всё.

Что это даёт: не нужно дублировать иконки/цвета/категории в JS на клиенте и в JSON на сервере. Одно место — модуль.

Принцип 10. Инструменты вокруг
npm run lint:api — проверка контракта модулей.

npm run build:registry — генерация реестра.

npm run check:layers — проверка, что каждый слой UI-конфига есть в реестре.

npm run doctor — общий health-check проекта (уже есть crucix-doctor).

npm run test — контрактные тесты.

Всё это — не «сделаем потом», а часть определения модуля. Добавить модуль = запустить npm run lint:api && npm run build:registry. Два шага. Всё остальное сгенерируется.

Что это всё вместе даёт
Если довести до такого состояния:

Нельзя добавить модуль с неправильным экспортом — ловит lint.

Нельзя добавить слой, которого нет в реестре — ловит check:layers.

Нельзя забыть добавить модуль в реестр — реестр генерируется автоматически.

Нельзя иметь 5 форм handler — контракт один.

Нельзя иметь пустой слой без предупреждения — API отдаёт 503 с явной причиной.

Нельзя запутаться в ошибках 500/404 — они различимы по коду.

Мониторинг видит, какие слои пусты, какие падают, какие не вызываются.

Как это разворачивается в реальности (порядок работ)
Не сразу всё. Порядок, при котором каждый шаг приносит пользу и не ломает остальное:

Шаг 1 (сейчас, малый). Расширить router.mjs — универсальный resolveHandler для 6 форм + auto-prefix с двумя ключами (dxy-api и dxy). Результат: 500-е уходят, слои начинают отвечать.

Шаг 2 (следующий, малый). Единый формат ответа: обёртка { type, meta, features }. Начать с 3-4 модулей. Затем постепенно.

Шаг 3 (средний). scripts/build-registry.mjs — генератор реестра из модулей. Реестр становится артефактом. Проверка npm run build:registry -- --check.

Шаг 4 (средний). /api/registry/layers — эндпоинт, который отдаёт список слоёв. Клиент начинает строить панель из него.

Шаг 5 (большой). Полный рефакторинг layers.js — вместо массива 238 объектов клиент дёргает /api/registry/layers. layers.js становится тонким загрузчиком.

Шаг 6 (большой). Тесты контракта. npm test ловит регрессии.

Шаг 7 (гигиена). Дубликаты слоёв (Уязвимости CVE × 2, Кибератаки × 3, USGS Earthquakes × 4) — консолидируются: один модуль на смысл, одна запись в реестре, одна иконка на панели.

Что мы можем начать делать прямо сейчас
Совместить Шаг 1 с заделом на Шаг 2. То есть:

Переписать router.mjs — универсальный resolveHandler + auto-prefix с двумя ключами + структурированный лог {layer, moduleId, status, form}.

Заодно — починить dxy-api.mjs и firms-api.mjs до канона (export async function handler). Это два живых примера для будущего контракта.

Тогда:

500-е уходят сразу (роутер поймёт default-объект и named-handler);

у 180 отсутствующих id появляется шанс найтись через auto-prefix без -api;

логи начинают показывать, какие формы где.

А после этого — уже можно идти на Шаг 3 (генератор реестра) и Шаг 5 (панель из API).
